## 1. 现状盘点（v3.0）

### 1.1 已建成

| 层 | 能力 | 位置 |
|---|---|---|
| 判别层 | 站点画像（SiteProfile）、四维合规判定 | `backend/discover/`、`backend/compliance/` |
| 采集层 | 能力注册表、三级去重、自适应限速、任务调度 | `backend/collect/` |
| 数据层 | 规范化、PII 最小化、数据集物化、字段级血缘 | `backend/pipeline/` |
| 分析层 | 六种分析、报告生成、三格式导出 | `backend/analysis/facade.py` |
| 工具层 | MCP 七工具、Bearer 鉴权、审计留痕 | `backend/mcp/` |
| 界面层 | 六页、设计系统、粒子背景、骨架屏、响应式 | `frontend/src/` |

规模：112 个 REST 端点 + 1 个 MCP 端点、105 个自动化测试、主包 1.07 MB（首屏 587 KB）。

### 1.2 盘点中发现的四个问题

**问题 1 · 测试污染生产库**（运维级，优先级高）

主库中堆积了 `dataset_smoke_local_*` 系列表——Smoke 契约测试每次运行创建一张新表，
从不清理。当前已有十余张且只增不减。

后果：库体积持续膨胀；数据表列表被测试表淹没，真实数据集难以辨认；
将来接 ClickHouse 或做保留策略时，这些脏表会干扰判断。

修复方向：测试使用独立库（或内存库）；加 teardown 清理；
并在测试里加一条断言——主库不应存在 `*_smoke_*` 表。

**问题 2 · `AGENTS.md` 已过时**

它描述的是重构前结构（旧路由清单、`crawlers/` 目录、Docker v2 等）。
新接手者按它找入口会全部落空。需要按当前结构重写。

**问题 3 · 画像库仍是"副产品"**

`SiteProfile` 目前只在采集流程中被顺带生成，没有独立的管理、检索、复用入口。
它的真正价值——**复用探测结果、跨站点模式迁移**——完全没有释放。
这是覆盖度提升最直接的杠杆，却最没有被用起来。

**问题 4 · 断点续传只做了数据结构**

`CollectTask.cursor` 已落库，但没有重入恢复逻辑。当前每个 job 只有单分片，
还不构成瓶颈，但一旦做分页遍历就会暴露。

## 2. 升级方向

四个维度，按「离用户价值由近及远」排列：

**维度 A · 从「手动采一次」到「持续自动采」**
现在是：输入 URL → 分析 → 采集 → 物化，每一步都要人点。
应该是：站点登记一次 → 定时或触发采集 → 增量更新 → 异常告警。

**维度 B · 从「能用」到「可信」**
数据平台的信誉来自可追溯：每条数据都能回答「从哪来、按什么规则采的、合规依据是什么」。
血缘已经有了，但缺界面、缺合规中心、缺审计检索——能力沉淀在表里却没人看得见。

**维度 C · 从「单数据集」到「数据资产」**
当前只能看单个数据集。资产化的标志是：能对比、能检索、能版本化、能定策略。

**维度 D · 从「本机」到「可部署」**
Hermes 接入、两形态协作、部署脚本、监控导出。

六个已有 + 九个新增 = 十五页。新增页面按价值分三档：

- **第一档（建议先做）**：站点库、数据集详情、合规中心、接入管理
- **第二档（其次）**：任务详情、调度中心、审计日志、运行监视
- **第三档（可选）**：对比分析、系统设置

### 4.2 导航分组调整

新增页面后，侧边栏分组需要调整。当前四组 → 五组：

```
总览
  工作台

采集链路
  站点分析 · 站点库 · 采集任务 · 调度中心

数据资产
  数据集 · 对比分析

  数据分析 · 分析报告

平台治理
  合规中心 · 审计日志 · 接入管理 · 运行监视 · 系统设置
```

「平台治理」组默认折叠，只显示组标题与计数徽标——治理类页面使用频率低，
不该与日常操作争抢注意力。

### 4.3 站点库 `/sites` · 第一档

**定位**：把画像从"采集的副产品"变成"可复用的资产"。

```
┌──────────────────────────────────────────────────────────────┐
│ 站点库                          [批量判别] [判定筛选▾] [搜索] │
├──────────────────────────────────────────────────────────────┤
│ 画像 24  ·  可采 18  ·  待确认 4  ·  不可采 2                 │
├──────────────────────────────────────────────────────────────┤
│ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐    │
│ │ example.com    │ │ news.site.cn   │ │ shop.demo.com  │    │
│ │ ● 可采 A1/B1   │ │ ● 待确认 A2/B4 │ │ ● 不可采 A4    │    │
│ │ 新闻 · 置信 .82│ │ 电商 · 置信 .71│ │ · 置信 .64     │    │
│ │ 字段 8 · 覆盖76%│ │ 字段 12 · 覆盖68%│ │ 上次 3 天前   │    │
│ │ 2 天前 · 3 次采集│ │ 用于 5 个任务  │ │                │    │
│ └────────────────┘ └────────────────┘ └────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

**关键交互**
- 卡片点击 → 右侧抽屉展开画像详情（结构 / 字段表 / 策略 / 判定历史）
- 「重新探测」→ `force_refresh=true`
- 多选 → 批量重新探测 / 导出画像 / 直接创建采集计划
- 顶部筛选：按判定结果（可采 / 待确认 / 不可采）、按站点类型

**数据来源**
- 列表：`GET /api/v1/discover/profiles`（已有）
- 详情：`GET /api/v1/discover/profiles/{id}`（已有）
- **需后端补**：统计聚合接口（各判定状态的计数、站点类型分布）

**状态处理**
- 加载：六张卡片骨架
- 空：引导「去分析第一个站点」并直达 `/discover`
- 过期标记：`last_verified` 超过 14 天的卡片加时间角标，提示重探测

**定位**：单个数据集的完整档案——schema、血缘、统计、版本、导出。

```
├───────────────────────────┬──────────────────────────────────┤
│ 字段概览                  │ 数据血缘                          │
│ ┌───────────────────────┐ │ title      ← json-ld:$.headline  │
│ │ 字段  类型  覆盖  PII │ │ publish_date ← json-ld:$.datePub…│
│ │ title text  100%  —   │ │ author     ← json-ld:$.author…   │
│ │ date  dt    100%  —   │ │ content    ← css:article         │
│ │ author text 100% 哈希 │ │                                  │
│ └───────────────────────┘ │ 隐私处理：author → hashed        │
├───────────────────────────┴──────────────────────────────────┤
│ 数据预览                                    [分页] [每页 50]  │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ source_url │ title │ publish_date │ author │ content ... │ │
│ └──────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**关键交互**
- 血缘行点击 → 高亮对应字段并显示提取规则详情
- 字段点「眼睛」→ 只看该列
- 导出按钮组：CSV / JSON / Excel

**数据来源**
- `GET /api/v1/collect/datasets/{id}/preview`（已有，含行数据）
- **需后端补**：数据集元信息接口（现在 `preview` 只返回行数据，
  缺 `name / schema / lineage / pii_policy / created_at`）。
  最小改动：在 `read_dataset` 的返回里带上 `dataset` 元信息。

### 4.5 合规中心 `/compliance` · 第一档

**定位**：把合规从"藏在表里"变成"看得见、可复核、能交接"。

```
┌──────────────────────────────────────────────────────────────┐
│ 合规中心                    [判定筛选▾] [时间范围▾] [导出]   │
├──────────────────────────────────────────────────────────────┤
│ 判定 142  ·  可执行 118  ·  待确认 18  ·  已阻断 6            │
├──────────────────────────────────────────────────────────────┤
│ 待确认（需补齐授权）                                          │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ news.site.cn    A2/B4   令牌 3f8a…  剩 41h  [补齐授权]  │ │
│ │ forum.demo.io   A2/B4   令牌已过期          [重新判别]  │ │
│ └──────────────────────────────────────────────────────────┘ │
├──────────────────────────────────────────────────────────────┤
│ 已阻断（附替代数据源）                                        │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ shop.demo.com  A4 技术隔离                                │ │
│ │ 替代：官方 API(.60) · RSS/Sitemap(.40) · 存档源(.35)      │ │
│ │ 综合可达率 0.99                       [查看详情]          │ │
│ └──────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**关键交互**
- 「补齐授权」→ 弹出授权依据表单（声明类型 + operator + 说明），写回判定记录
- 令牌状态可视化：剩余有效期倒计时，过期标红
- 点击某条判定 → 展开完整四维取证（reasons 逐条列出）

**数据来源**
- `GET /api/v1/discover/verdicts`（已有）
- **需后端补**：授权声明写回接口（`PATCH /verdicts/{id}`：设置 authorization_basis / operator）

**为什么这页值得做**

它是「合规必须落成代码」这个设计的外显面。没有它，合规判定就只是一堆数据库记录；
有了它，整套机制才能被复核、被交接、被外部信任——这正是平台对外最硬的差异点。

**关键交互**
- 新建规则：选计划 → 设频率（cron 可视化选择器，不要求用户手写表达式）
- 每次执行结果以「近期点阵」呈现（一眼看出稳定性），点击某次跳到对应任务详情
- 暂停/启用开关；暂停时保留历史

**数据来源**：**全部需后端补**
- `schedules` 表（plan_id, cron, enabled, last_run, next_run, run_count, fail_count）
- `GET/POST/PATCH/DELETE /api/v1/collect/schedules`
- 调度执行依赖 Celery beat 或 APScheduler

**注意**：调度的失败重试必须与三级去重联动，否则网络抖动会造成重复入库。
建议策略：失败任务照常重试，但重试时强制走内容级去重（已有实现）。

## 5. 实施路线

### P7 · 自动化闭环（约 10 天）

**目标**：从"手动采一次"变成"登记后持续采"。

- E2 定时调度 + `/schedules` 页
- E3 断点续传重入恢复
- `/sites` 站点库
- `/collect/:jobId` 任务详情

**验收**：登记一个站点 → 建一条每小时调度 → 连续跑 3 次 → 第二次起增量命中生效、
条目数不增长、任务详情能看到完整的降级链与去重统计。

### P8 · 治理与可观测（约 9 天）

**目标**：让能力变得可复核、可交接。

- D1 测试库隔离 + 清理已有脏表
- C1 合规中心 + `/compliance` 页
- C2 审计检索 + `/audit` 页
- O1 运行监视 + `/monitor` 页
- O6 `AGENTS.md` 重写

**验收**：任取一条数据，能沿着「数据 → 血缘 → 提取规则 → 画像 → 判定 → 审计记录」
一路回答到"谁在什么时候、依据什么采的"。

### P9 · 数据资产深化（约 10 天）

- D2 数据版本与快照、D3 保留策略、D4 检索层
- `/datasets/:id` 数据集详情
- A1 多数据集对比 + `/compare` 页

**验收**：同一站点两次采集产生的数据集能对比出字段与数值差异；
大数据集能按字段值检索。

### P10 · 生产化与协作（约 11 天）

- O2 MCP 部署脚本、O3 两形态协作、O4 指标导出、O5 备份恢复
- `/integrations` 接入管理

**验收**：Hermes 通过 MCP 端点完成「分析 → 采集 → 分析 → 报告」完整闭环，
且全过程可在审计日志中回溯。

### 顺序理由

**P7 必须先行**：自动化是「数据需求直接适用」的前提。没有调度，平台只是个更聪明的
手动工具；有了调度，它才是一个可以托付的系统。

**P8 紧随其后**：治理能力越晚做，历史数据的可追溯性越差——审计日志只能记录从
接入那天起发生的事。且 D1（清脏表）越早做代价越小。

**P9/P10 是深化**：它们提升上限，但不改变平台的可用性底线。

## 6. 取舍与边界

### 6.1 明确不做

- **不做通用 BI**：不替代 Superset / Metabase。分析能力服务于"刚采回来的数据"，
  不是给已有数仓做看板。
- **不做可视化拖拽建模**：配置即代码，界面只做配置与观测。
- **不做多租户计费**：当前是单用户 + principal 标识，不做租户隔离与配额。
- **页面数量上限 15**：新增页面必须能回答"它替代了哪一次手工操作"。
  超过这个数，每个页面的完成度都会被稀释——**页面多不是目标，覆盖工作流才是**。

### 6.2 3D 元素的边界

粒子背景已经够用。**不建议引入 three.js**：它会让前端体积翻倍（+600 KB 起）、
低端机掉帧，而收益只是"更炫"。展示型项目的加分点在于**信息密度与专业感**，
不在动效数量——一个响应 200ms、布局不跳动的数据平台，比一个粒子飞舞但卡顿的平台
更像工程作品。

### 6.3 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 调度 + 重试造成重复采集 | 数据重复 | 三级去重已兜底；重试时强制走内容级去重 |
| 站点改版致画像失效 | 采集静默失败 | C4 画像失效监控 + 自动重探测 |
| 数据量超 100 万行 | SQLite 成瓶颈 | 阈值触发切 PostgreSQL（接口已抽象） |
| 测试继续污染主库 | 库膨胀 | D1 优先级提到 P8 首位 |
| `_legacy` 目录累积 | 仓库臃肿 | 定期评估；确认无参考价值后归档到独立分支 |

## 7. 如果只做三件事

1. **D1 测试库隔离 + 清脏表**（1 天）—— 现在就能做，而且越拖越脏
2. **`/sites` 站点库**（2 天）—— 杠杆最高：把已经在数据库里的画像变成可复用的资产
3. **E2 定时调度**（4 天）—— 决定这个平台是"工具"还是"系统"

这三件做完，平台就从「能被调用」变成「能被托付」。其余都是在这之上的增量。
